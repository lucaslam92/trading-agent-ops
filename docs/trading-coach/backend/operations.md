# Trading Coach 运行、容量与发布设计

状态：首版默认预算与操作流程，尚未实现脚本或测量。配套：[后端架构](architecture.md)、[一致性与恢复](consistency-and-recovery.md)、[接口契约](../shared/api-contracts.md)。

## 1. 资源预算与超时

默认验证环境：2 vCPU、2 GiB 内存、本地 SSD，单 JVM，初始最大堆 1 GiB。以下为可配置上限；不得以虚拟线程数量代替容量管理。队列同时受条数和估算字节数限制，先到者生效。

| 项目 | 默认值 | 达到上限时的行为 |
| --- | --- | --- |
| 固定采集序列 | 12 | 配置超过 allowlist 启动失败 |
| REST 上游在途请求 | 全 provider 共 4 个；等待队列 64 | 历史查询返回 503 `CAPACITY_EXCEEDED`；实时对账优先，受 provider 限流约束 |
| 上游连接 / 单请求超时 | 5 秒 / 10 秒 | 可重试错误最多 3 次总尝试，退避 1、2 秒加 jitter；Retry-After 超过剩余预算则本轮终止 |
| 单次对账 / 重建 | 120 秒 / 120 秒 | 超时标记 DEGRADED 并取消；自动重试间隔至少 30 秒，最多连续 3 轮，之后等待人工恢复 |
| 每序列输入 / 重建暂存 | 各 4,096 条或 8 MiB；全局合计 128 MiB | 停止该订阅并通过 REST 恢复，不能静默跳过已收盘数据 |
| 重建并发 / 等待队列 | 2 / 12 | 同序列任务去重；拒绝新增任务并报告 CAPACITY_EXCEEDED |
| SQLite 写队列 | 256 个批次或 16 MiB | 限制历史导入；实时提交超时后暂停该序列并进入 DEGRADED |
| 历史写入批次 | 最多 500 根；每轮至多 1 批历史后检查实时队列 | 为实时收盘让出调度机会，不持有跨批次事务 |
| SQLite busy_timeout / 写任务期限 | 1 秒 / 5 秒（含排队与重试） | 仅明确回滚的 BUSY 最多重试 2 次；结果不明先对账，不直接重试提交 |
| SSE 连接数 | 全局 32，每来源地址 16 | 429 `RATE_LIMITED`，带 Retry-After；仅信任已配置代理的转发地址 |
| 每序列 SSE ring | 512 批或 8 MiB | 丢弃最旧批次，旧 token 走 snapshot |
| 每客户端实时发送队列 | 128 批或 2 MiB | 关闭慢客户端；重连重新选择补发或 snapshot |
| 一次可补发历史 | 最多 64 批且 512 KiB | 超出直接 snapshot，不将 512 批塞入 128 批队列 |
| SSE 单增量 / snapshot | 512 KiB / 2 MiB（UTF-8 编码后） | 增量过大走 snapshot；snapshot 仍过大则暂停该序列发布并报告 CAPACITY_EXCEEDED，不能截断 JSON 或漏掉转换 |
| 全局 SSE 编码数据预算 | 256 MiB | 拒绝新订阅并清理慢连接；预算覆盖 ring、补发副本、队列和快照，构造前预留空间 |
| SSE 心跳 / 发送期限 / Servlet 异步寿命 | 15 秒 / 10 秒 / 30 分钟 | 发送超时关闭连接；异步寿命结束后按 token 重连；代理 read timeout 为 60 秒 |
| HTTP 数据请求期限 | 15 秒 | 503 `QUERY_TIMEOUT`；结束读事务并取消关联工作，不取消其他客户端共用的采集 |
| `/candles` 单页 | 1–1,000，默认 500 | 无效参数返回 422 |
| `/annotations` 单次范围 / 数量 | 最多 2,000 个周期跨度、2,000 条/页 | 范围过大 422 `QUERY_RANGE_TOO_LARGE`；数量超出返回分页游标，不截断后声称完整 |
| 历史图表缓存 | 最多 10,000 根 Candle、20,000 条标注、5,000 个 Swing | 淘汰远离当前视口的历史页，当前视口优先；用户缩小到可显示范围，按需重新加载 |
| 可视范围 | 最多 2,000 根 Candle | 超出时提示缩小范围；不通过省略 K 线假装完整绘制 |
| 优雅停止期限 | 30 秒 | 记录未完成任务，重启从持久化边界恢复 |

输入待处理、数据库待写和前端缓存都记录当前使用量。SSE sender 的 deadline 需要容器写超时或可关闭的底层连接配合，不能仅依赖 Future.cancel；P2 必须用完全不读取 socket 的客户端验证线程和连接确实释放。

普通 HTTP 查询每来源地址每秒 10 次、burst 20，超出返回 429；历史缺失回补按序列和范围合并请求，单客户端不能创建无限上游任务。`/annotations` 的 from/to 必须对齐周期，计算跨度时先验证有界整数以避免溢出。默认预算进入配置校验与运维指标；调大预算须重新压测并记录机器信息。

## 2. 备份与恢复目标

首版目标：备份间隔 1 小时，RPO ≤ 1 小时；恢复已有本地数据并能提供标明状态的查询 RTO ≤ 30 分钟。真实行情恢复另受上游可用性影响，不把网络恢复时间承诺为本地 RTO。目标须在实际历史量上演练，超出时提前引入 checkpoint 或提高资源预算。

备份使用 SQLite Online Backup API 或经过验证的 SQLite CLI `.backup`，禁止对运行中的 WAL 数据库只复制主 `.sqlite3` 文件。实现依据：[SQLite Backup API](https://www.sqlite.org/backup.html) 与 [WAL](https://www.sqlite.org/wal.html)。若目标 Java 驱动的备份入口尚未验证，部署脚本可使用同版本兼容的 CLI，P4 验证后锁定版本。

每次备份流程：

1. 写入新的临时目标，设置总期限 5 分钟和有限 BUSY 重试，不覆盖最后一个成功备份。
2. 关闭目标连接，在备份库执行 `PRAGMA integrity_check` 和 `PRAGMA foreign_key_check`；前者为 ok、后者零行才可发布。二者验证范围不同，必须分别检查。[SQLite PRAGMA](https://www.sqlite.org/pragma.html#pragma_integrity_check)
3. 从备份库本身读取 schema 版本、每序列 ACTIVE 版本、处理边界、配置与元数据版本，写入 manifest；另记录运行中的应用构建 SHA、备份时间和文件 SHA-256。配置包只含非敏感内容；备份与发布操作互斥，避免构建版本记录跨越升级。
4. 原子改名为完成状态，并复制到独立于应用数据盘的位置。复制失败仍视作未达到备份目标，产生告警。
5. 保留最近 24 个小时备份及 7 个每日备份；最近一个已验证备份始终保留。距最近成功备份超过 65 分钟告警。

恢复步骤：停止所有应用实例并确认数据目录无占用 → 保留故障数据库及 WAL/SHM 以供排查 → 在新目录恢复已验证备份 → 校验 checksum、integrity、外键和 schema 兼容性 → 使用匹配的应用版本及配置启动单实例 → 从数据库 ACTIVE 代重建，新 epoch 同步 → 按持久化边界向上游回补。成功检查前不覆盖故障目录，不能把旧 WAL/SHM 配到恢复后的数据库旁边。

每月及首次发布前，必须在独立目录完成一次恢复演练，记录实际丢失窗口、恢复耗时、各序列最后处理时间和数据缺口。只备份成功不算恢复验收通过。

## 3. 升级与回滚

发布包包含后端构建、前端静态产物、契约版本、配置模板、SQL migration 校验和清单、支持的 schema 版本范围。后端 Gradle、前端 lockfile 和数据库驱动版本固定。启动发现数据库 schema 超出兼容范围则失败，不尝试猜测兼容。

单实例首版采用维护窗口发布：

1. CI 通过契约、算法、真实 SQLite、前端构建和 E2E；用生产备份副本演练 migration 及重启。
2. 代理进入维护模式，停止旧应用；取得升级前一致备份、配置和旧构建，检查恢复包可用。
3. 在本地持久卷上持有应用独占锁，验证 SQL 校验和并执行 migration；新程序启动重建，准备完成前维持维护模式。数据库 migration 成功不等于应用发布成功。
4. 检查每序列当前版本、处理状态、REST / SSE、日志与无混版数据后，切换前端静态产物并解除维护。客户端检测契约不兼容时提示刷新，不吞掉解析错误。

回滚依据 schema 兼容范围决定：旧构建明确兼容当前 schema 时可停止新应用后切回；不兼容时恢复升级前数据库、配置和旧构建，再回补发布后行情。首版不自动执行破坏性 down migration。升级验收前不删旧字段或退休结果；删列 / 改语义需单独迁移版本和已验证备份。

操作脚本必须保证启动互斥，不能仅在文档中要求“副本数=1”。升级期间新增的行情可回补，但 firstSeenAt 等运行时事实可能无法从上游复原；回滚记录要明确这一点。

## 4. 磁盘、健康与告警

- 可用磁盘低于 20% 或 2 GiB 时告警；低于 10% 或 1 GiB 时停止历史扩展、新重建和写入，进入 `DEGRADED / STORAGE_LOW`。不能为腾空间自动删除 ACTIVE 分析历史。新建完整代前还要检查能够容纳一份源代副本及安全余量。
- 数据库、writer 或所有序列处理器不可恢复时 readiness=503；单序列 REBUILDING / DEGRADED、上游短断线不触发进程 liveness 失败，其影响在各序列状态呈现。
- 指标至少包括：行情延迟、处理延迟、processing 状态、重建耗时、输入 / 写队列深度、SSE 客户端和重同步次数、进程内存、WAL 大小、磁盘可用量、备份年龄。
- READY 状态下收盘处理落后超过 5 秒持续 30 秒、DEGRADED 持续 60 秒、队列使用超过 80% 持续 30 秒、重建超过 120 秒均告警。WAL 超过 256 MiB 持续 5 分钟检查长读事务；不在线删除 WAL 文件。
- 日志保留 7 天且总量不超过 1 GiB；记录 requestId / series / epoch / seq / datasetRevision / build SHA，避免记录秘密和无限量原始行情。

## 5. 交付验证

P4 前需交付实际备份 / 恢复 / 发布脚本、版本兼容检查、单实例锁及上述监控。验收包含：持续写入时备份、损坏备份被拒绝、磁盘不足、migration 中断、升级后应用启动失败、旧程序拒绝不兼容 schema、慢客户端和大量补发、内存与队列预算。测试结果附机器、数据规模和耗时；本页数字为设计默认值，不是压测结果。
