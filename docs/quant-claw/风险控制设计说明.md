# Quant Claw 风险控制设计说明

## 1. 文档目的

本文档用于说明 `quant-claw` 的风险控制设计思路，包括当前已实现能力、建议的风控分层、限额模型以及后续应补充的安全控制。

## 2. 当前已实现的风控能力

当前 MVP 中，风控主要由 `ClawRiskAgent` 负责，已具备以下基础能力：

- 接收策略提案 `strategy.proposal.created`
- 读取提案中的 `risk_context`
- 根据请求名义本金进行限额判断
- 输出通过或拒绝结果：
  - `risk.check.approved`
  - `risk.check.rejected`
- 在结果中返回：
  - `approved_notional_usd`
  - `max_leverage`
  - `constraints`
  - `reason_codes`

当前默认示例限制：

- 单策略最大名义本金：`30000`
- 最大杠杆：`1.5`
- 最大滑点：`10 bps`

## 3. 为什么风控要单独成层

如果策略、风控、执行混在一起，会带来几个问题：

- 策略开发者容易绕过风控
- 风控规则难以集中治理
- 执行逻辑会承担不该承担的风险判断
- 后续实盘时很难插入审批、熔断和审计控制

因此，当前架构把风控放在策略提案和执行请求之间，是对的。

## 4. 建议的风控分层

建议把风控分成至少四层：

### 第一层：提案级风控

目标：在提案进入执行前，先筛掉明显不合理请求。

典型检查：
- 单次提案名义本金上限
- 单次提案最大杠杆
- 单次提案允许的最大滑点
- 标的是否在允许交易清单中

### 第二层：策略级风控

目标：控制单个策略的累积风险。

典型检查：
- 单策略总敞口上限
- 单策略净敞口上限
- 单策略日内亏损限制
- 单策略并发订单数限制

### 第三层：团队 / 账户级风控

目标：从更高层看整体风险，而不只看单条策略。

典型检查：
- team 级 gross exposure
- team 级 net exposure
- 账户级保证金占用限制
- 总回撤熔断
- 多策略间相关性风险

### 第四层：运行时安全控制

目标：在系统异常或市场异常时，阻止风险扩大。

典型控制：
- kill switch
- market halt / venue unavailable 保护
- 行情异常跳变检测
- 执行异常率过高熔断
- 风控服务不可用时禁止自动下单

## 5. 当前限额模型建议

MVP 阶段建议先把限额模型定得简单但明确。

### 建议基础限额项

- `max_proposal_notional_usd`
- `max_symbol_gross_usd`
- `max_team_gross_usd`
- `max_account_drawdown_pct`
- `max_order_slippage_bps`
- `max_open_orders`

### 为什么先做简单模型

因为当前阶段最重要的是：

- 先让规则可解释
- 先让结果可测试
- 先让拒绝原因可追踪

而不是一开始堆太多复杂数学模型，最后没人敢改、也没人能验证。

## 6. Reason Code 设计建议

为了让风控结果更可维护，建议拒绝与通过都使用结构化 reason code。

### 当前已出现的 code

- `LIMIT_OK`
- `STRATEGY_NOTIONAL_LIMIT_EXCEEDED`

### 建议后续补充

- `SYMBOL_NOT_ALLOWED`
- `TEAM_GROSS_LIMIT_EXCEEDED`
- `ACCOUNT_DRAWDOWN_LIMIT_EXCEEDED`
- `MAX_LEVERAGE_EXCEEDED`
- `MAX_SLIPPAGE_EXCEEDED`
- `VENUE_UNAVAILABLE`
- `KILL_SWITCH_ACTIVE`
- `RISK_SERVICE_DEGRADED`

## 7. Kill Switch 设计建议

Kill switch 是走向实盘前必须具备的能力。

建议至少支持三层：

### 策略级 Kill Switch

只停某个策略，不影响整个系统。

### Team 级 Kill Switch

暂停一个 team 下的所有策略与执行动作。

### 全局 Kill Switch

在严重异常时，全局阻断执行请求流入执行层。

## 8. 拒绝与审批策略建议

当前 MVP 中，风控是自动化通过 / 拒绝。后续可以扩展为：

- 自动通过
- 自动拒绝
- 人工审批后通过
- 人工确认后拒绝

这对接近实盘尤其重要。

## 9. 风控与执行的关系

建议始终坚持：

- 策略负责提出想法
- 风控负责判断能不能做
- 执行负责把允许做的事落地

不要让执行层承担“临时帮忙风控”的职责，也不要让策略层偷偷带入执行限制判断。

后续建议再补以下配套文档：

- 风控 reason code 字典
- 限额配置说明
- 风控审批流设计
- kill switch 操作手册
- 风控测试用例矩阵

## 11. 当前结论

对 `quant-claw` 来说，风控不是附属模块，而是把“策略想法”变成“可执行动作”前最关键的一道门。

MVP 阶段不要求风控特别复杂，但必须做到：

- 规则明确
- 输出结构化
- 拒绝原因可追踪
- 后续可扩展到策略级、团队级、账户级和运行时保护
