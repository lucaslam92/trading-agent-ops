# Quant Claw 消息协议说明

## 1. 文档目的

本文档用于说明 `quant-claw` 当前各个 Agent / Service 之间是如何通过事件进行通信的，包括：

- Topic 命名规范
- 消息流转关系
- 各类事件的生产者与消费者
- 当前实现中的协议边界

## 2. 协议设计原则

当前系统采用**事件驱动协议**，核心原则如下：

1. 所有跨模块协作都通过统一事件信封传递
2. Topic 命名采用 `domain.entity.action` 风格
3. 业务数据放入 `payload`
4. 事件由生产者负责声明语义，由消费者按契约解析
5. 每一跳尽量只做一件事，避免单个 Agent 承担多重职责

## 3. 当前 Topic 列表

### 市场域

- `market.funding.updated`
  - 含义：资金费率更新
  - 生产者：`MarketDataService`
  - 消费者：`ClawQuantAgent`

### 策略域

- `strategy.proposal.created`
  - 含义：策略提案已生成
  - 生产者：`ClawQuantAgent`
  - 消费者：`ClawRiskAgent`

### 风控域

- `risk.check.approved`
  - 含义：风控审批通过
  - 生产者：`ClawRiskAgent`
  - 消费者：`ClawTraderAgent`

- `risk.check.rejected`
  - 含义：风控审批拒绝
  - 生产者：`ClawRiskAgent`
  - 消费者：持久化服务 / 审计逻辑

### 执行域

- `execution.order.requested`
  - 含义：已生成执行请求
  - 生产者：`ClawTraderAgent`
  - 消费者：`ExecutionGateway`

- `execution.order.filled`
  - 含义：订单已成交
  - 生产者：`ExecutionGateway`
  - 消费者：`PortfolioEngine`

### 组合 / 持仓域

- `portfolio.position.updated`
  - 含义：持仓已更新
  - 生产者：`PortfolioEngine`
  - 消费者：持久化 / API 查询侧

## 4. 主消息流

```text
MarketDataService
  -> market.funding.updated
     -> ClawQuantAgent
        -> strategy.proposal.created
           -> ClawRiskAgent
              -> risk.check.approved
                 -> ClawTraderAgent
                    -> execution.order.requested
                       -> ExecutionGateway
                          -> execution.order.filled
                             -> PortfolioEngine
                                -> portfolio.position.updated
```

拒绝路径：

```text
ClawRiskAgent
  -> risk.check.rejected
```

## 5. 事件信封格式

当前系统统一使用 `Event` 模型作为传输信封，结构如下：

```json
{
  "event_id": "evt_xxx",
  "topic": "strategy.proposal.created",
  "ts": 1773790000000,
  "source": "claw_quant",
  "payload": {}
}
```

字段含义：

- `event_id`：事件唯一 ID
- `topic`：事件主题
- `ts`：事件时间戳（毫秒）
- `source`：事件来源模块 / Agent
- `payload`：具体业务载荷

## 6. 当前总线实现

### InMemoryEventBus

适用场景：
- 本地开发
- 单进程调试
- simulation 测试

特点：
- 简单直接
- 易调试
- 无外部依赖
- 不适合多实例部署

### RedisEventBus

适用场景：
- 多进程 / 多实例联通
- 更接近生产环境的消息流模拟

特点：
- 基于 Redis Pub/Sub
- 发布为 best-effort
- 每个 topic 独立监听任务
- 当前仍属于 MVP 级轻量实现

## 7. 协议约束建议

为避免后续系统变大后协议漂移，建议遵守：

1. 不要在 topic 名里塞版本号和业务细节
2. 业务字段统一进入 `payload`
3. 不同领域对象使用不同模型表达
4. 破坏性变更需要做 schema 版本管理
5. 每新增关键 topic，都要补 simulation 测试

## 8. 后续建议新增的 Topic

可按以下方向扩展：

- `market.price.tick`
- `market.orderbook.updated`
- `strategy.signal.generated`
- `risk.limit.triggered`
- `execution.order.cancel_requested`
- `execution.order.canceled`
- `portfolio.pnl.updated`
- `audit.event.recorded`

## 9. 当前协议边界总结

当前协议已经足够支撑 MVP 闭环，但仍然偏轻量。下一步最值得补的是：

- 更正式的 payload 字段约束
- 更完整的订单生命周期 topic
- 风控拒绝原因的标准码体系
- 重放 / 幂等处理策略
