# Quant Claw 术语表与概念词典

## 1. 文档目的

本文档用于统一 `quant-claw` 项目中的关键术语，降低沟通歧义，方便后续文档、代码、接口和评审使用同一套语言体系。

## 2. 核心术语

### Agent

系统中的自治角色单元。每个 Agent 只关注某一类输入事件，并对外输出特定结果。

当前典型 Agent 包括：
- `ClawQuantAgent`
- `ClawRiskAgent`
- `ClawTraderAgent`

### Service

系统中的服务型组件，负责提供编排、执行、持久化、市场数据、组合更新等能力。和 Agent 相比，Service 更偏基础设施或执行支撑。

### Team

策略团队或运行团队的逻辑编排单元。一个 Team 可以包含：

- 一组交易标的
- 一组启用的 Agent
- 一组启用的策略

例如：`btc-eth-focus`

### Strategy

策略逻辑本身，决定在什么市场条件下提出什么交易想法。当前 MVP 里的示例策略是：

- `funding_rate_arb`

### Signal

策略发现的交易信号。它通常先于正式提案存在，代表“发现了一个可能值得交易的机会”。

### Proposal / StrategyProposal

策略提案，表示由策略 Agent 生成、但尚未经过风控审批的可执行交易想法。

### RiskDecision

风控决策，表示风控模块对某个提案作出的通过或拒绝判断。

### ExecutionOrder

执行订单请求，表示已经从“提案 / 风控”阶段进入“执行”阶段的具体下单请求。

### Position / PositionSnapshot

持仓状态快照，用来表达账户 / 策略 / 标的当前持仓结果。

### Event

系统内模块之间通信的统一事件信封。所有跨模块协作都依赖事件流完成。

### Topic

事件主题，用于标识某类事件的语义，例如：

- `market.funding.updated`
- `strategy.proposal.created`
- `risk.check.approved`

### Payload

事件中实际承载的业务数据。Event 是信封，Payload 是正文。

## 3. 交易与运行术语

### Paper Trading

纸面交易。使用真实或近似真实的交易逻辑，但不下真实资金订单。

### Simulation

模拟环境。通常使用 mock 或 replay 数据来驱动系统，重点是验证链路是否正确。

### Backtest

回测环境。使用历史数据进行离线复盘，重点是检验策略历史表现与可重复性。

### Live Trading

实盘环境。接真实交易所、使用真实资金、承担真实风险。

### Venue

执行场所或交易 venue，例如现货市场、永续合约市场，或未来不同交易所连接点。

### Broker Adapter

执行适配器，用来连接具体执行环境，例如 paper broker 或未来的真实交易所接口。

## 4. 风控术语

### Notional

名义本金，用来衡量一次提案或订单所对应的风险规模。

### Gross Exposure

总敞口，不区分多空方向，反映总体暴露规模。

### Net Exposure

净敞口，反映多空轧差后的方向性暴露。

### Leverage

杠杆倍数。

### Slippage

滑点，表示预期价格与实际成交价格之间的偏差。

### Kill Switch

紧急停止开关，用于在异常情况下中止下单、停止策略或切断执行链路。

### Reason Code

原因码，用于结构化表达风控通过 / 拒绝或执行异常的原因。

## 5. 工程术语

### Orchestrator

编排器。负责把 Agent、Service、EventBus、Persistence 等模块组装起来，建立整个运行链路。

### Event Bus

事件总线，负责在各模块之间传递事件。当前有：

- `InMemoryEventBus`
- `RedisEventBus`

### Persistence

持久化能力，负责保存事件、提案、风控决策、订单和持仓等数据。

### Idempotency

幂等性。即同一个请求或事件被重复处理时，不应该产生重复副作用。

### Replay

事件重放。基于历史事件重新驱动系统，用于测试、排障或回测。

## 6. 统一表达建议

后续文档、接口、PR、代码评审中，建议统一使用以下表达：

- 用“提案”指代 `StrategyProposal`
- 用“风控决策”指代 `RiskDecision`
- 用“执行请求”指代 `ExecutionOrder`
- 用“事件信封”指代 `Event`
- 用“业务载荷”指代 `payload`
- 用“模拟盘 / Simulation”区分于“纸面交易 / Paper Trading”

## 7. 当前结论

如果没有统一术语，系统越大越容易沟通错位。这个词典的作用不是追求学术，而是让：

- 产品说的词
- 架构文档里的词
- 代码里的模型名
- API 里的字段语义

尽量保持同构。
